# Search

P3-02 establishes the Haskell query-planning and SQLite FTS retrieval boundary. It classifies identifier, keyword, and prose queries; preserves phrase and exact-term expressions without truncation while independently capping the NEAR, prefix, Porter, and identifier fallbacks; extracts ordered local acronym aliases; and exposes the same six summary/passage FTS5 schemas, tokenizers, and BM25 field weights as the statically reviewed prototype.

Collapsed summary retrieval applies allowed item IDs inside each parameterized SQL query, uses deterministic 700-ID batches, negates BM25 so larger scores are better, orders ties by descending item ID, and merges duplicate IDs by maximum score. Candidate limits are positive and overflow-checked. Exact-AND and NEAR coverage—not phrase coverage—controls the prefix fallback, and the merged exact-term channel is intentionally not capped a second time.

This phase does not persist search materializations, fuse channels with reciprocal-rank fusion, apply public search filters or explanations, create source chunks, or expose CLI/provider behavior. Those remain later search phases. Normal tests read Haskell-owned retrieval goldens; regeneration is an explicit Haskell-only action and never runs the Python prototype.

P3-03 adds the disposable current-search materialization. It validates a revision-local Haskell snapshot, consumes the P2 reducer's validated current decision and connection heads, and atomically replaces ordinary document, alias, and ADR-section rows plus all six FTS populations. A resolved decision uses its ADR ID; decision conflicts retain one `ADR@record` item per sorted head. Scope, domain, and status remain independent, obsolete rows stay stored for a later explicit visibility override, and superseded or quarantined evidence is never indexed.

Current ADR sections are chunked independently using the deterministic 4 MiB/1500-character/300-overlap text core and stable passage IDs with section kind, ordinal, and one-based line range. This is distinct from P3-05 arbitrary source-file relevance. P3-04 consumes this materialization for vectors, public filters, weighted fusion, reranking, grouping, and explanations; cache publication, incremental compilation, CLI, web, providers, and CI/CD remain later work.

P3-04 adds the collapsed current-search service. Requests select `fts`, `vector`, or `hybrid` retrieval, validate limits from 1 through 1000, and apply obsolete, domain, file-scope, actor, and inclusive time filters before producing candidates. Blank queries remain deterministic filtered ADR listings whose `source_paths` contain only the effective decision, scope, domain, and status provenance, in that order with absent or conflicted axes omitted. Nonblank matched-candidate `source_paths` remain the selected search document's evidence paths. Nonblank queries fuse only active nonempty channels with weighted reciprocal-rank fusion at `k = 20`; raw channel scores establish rank, ties use descending item identity, and a bounded exact section pass plus bounded lexical/agreement bonuses reranks the leading candidates. Decision-conflict heads are scored independently and then grouped into one logical ADR: the logical row uses the title `[conflicted ADR]` and the ordered candidate-summary join, while the selected matched head remains separate evidence alongside the structured conflict explanation.

The Haskell service returns the `adrai/search/v1` projection with six-decimal finite numeric scores, channel ranks, lexical fields and terms, best-section evidence, FTS/vector diagnostics, filter outcomes, and a separate ranking-contract fingerprint. Vector search reuses the mandatory dependency-free Haskell embedders. Identifier FTS consumes P3-03's normalized identifier field, while identifier vectors consume the raw newline-delimited title, summary, full stripped Markdown body, space-joined domains, and rationale. Normal golden tests are read-only; `--write-p3-04-goldens` is the only regeneration path.

P3-04 intentionally deferred exploded or arbitrary source-file retrieval and passage-FTS rescue to P3-05. P3-06 now owns the executable quality and bounded-scale gates plus a reusable in-memory corpus seam; CLI/Explorer wiring remains P6; E2E and CI/CD remain final, low-priority delivery work.

P3-05 adds arbitrary raw-text relevance without teaching the query service to read the filesystem or invoke Git. The caller supplies typed revision or worktree bytes together with already-resolved path, revision, and blob identities. Revision sources must match the compiled snapshot; worktree sources are accepted only for a `HEAD`-bound snapshot. P4-01 through P4-03 now connect exact-OID Git observation to managed-document compilation and current-ADR search materialization. Arbitrary relevance-source discovery, dirty or untracked relevance input, and its public path-safety policy remain later work.

The decoder enforces the 4 MiB raw-byte limit before decoding, rejects NUL bytes and a control-byte ratio above 20 percent in a deterministic 16 KiB head/tail sample, decodes UTF-8 leniently, and normalizes newlines. Source text is split using the frozen 1500-character target, 300-character overlap, and 220-character newline radius, then reduced to at most 24 informative chunks. Fewer than 24 meaningful alphanumeric characters produce an empty result rather than a weak match.

Relevant ADR candidates combine exact summary and identifier scans with per-source-chunk passage FTS rescue and source semantic and identifier vectors. Relevance passage queries intentionally do not expand ADR-local aliases. The bounded shortlist is reranked against source chunks and stored ADR passage vectors; a corpus of at most 50,000 eligible passages uses exhaustive comparison, while a larger corpus uses the deterministic in-memory LSH seed and always exact-reranks the resulting candidates. The pure 50,000/50,001 boundary and the lower-level LSH primitives have dedicated vector tests. Obsolete ADRs remain opt-in. File scope contributes only a ranking bonus and never filters eligibility. Decision-conflict candidates are scored independently and grouped into one logical ADR while preserving the matched head as evidence.

The `adrai/relevant/v1` projection publishes finite six-decimal scores, up to three independent evidence excerpts, global pre-limit confidence and result margins, conflict metadata, and explicit scoring diagnostics. The Haskell-owned golden wrapper separately freezes the compact raw-text fingerprint and scoring contract. Normal golden tests are read-only; `--write-p3-05-goldens` is the only Haskell-owned regeneration path and never executes or imports the protected Python prototype. P3-06 now supplies the corpus quality, bounded-scale, hard-negative, and identifier-quality gates; real Git/worktree resolution remains the later integration boundary; CLI/Explorer exposure remains P6; CI/CD stays lowest priority.

P3-06 adds executable retrieval and relevance quality evidence. The Haskell-owned `adrai-relevance-six:v1` fixture uses seed 260729 and is materialized through the production snapshot/compiler boundary. All six primary cross-format sources retain their intended ADR within the top three, including literal-path, extensionless, and renamed-extension cases. Separate executable cases recover multiple real ADRs from a large noisy source, keep boilerplate/empty/tiny/scope-only hard negatives below their confidence ceilings, and require useful identifier and matched-term evidence for configuration, health, secrets, lease-token, and acknowledge-after-commit vocabulary.

The frozen Dropwire JSON is intentionally narrower: it validates the exact recorded result aggregate—22 cases, 47 expected associations, the recorded K-hit thresholds, and zero medium/high-confidence false positives. Its source corpus is absent. P3-06 did not reconstruct or execute that corpus, so the artifact is result-contract validation and never an executable parity claim.

`SearchVectorCorpus` is a reusable process-local corpus for one exact `SearchMaterialization`. Its compatibility fingerprint covers sorted document and passage identities, their exact embedding inputs—including the raw identifier-vector source rather than the normalized FTS text—and both release vector IDs. Every stored summary, identifier, and section vector is embedded once and immediately round-tripped through the canonical little-endian float32 representation before scoring. Search queries and relevance source chunks remain request-ephemeral. Compatibility wrappers build a corpus and delegate; explicit corpus APIs validate it before any query shortcut or SQLite work. Cold-built, reused, and repeated paths have identical typed projections and exact rendered bytes. Build/reuse origin is not exposed in public diagnostics.

The deterministic seed-0 scale integration materializes 2,000 logical ADRs into 2,000 search documents and 12,000 passages, persists the real SQLite index, and exercises both search and relevance through one reusable corpus. The original unique tail query `Architecture rule 1999` and additional stable marker probes retrieve their intended ADRs. A shared Haskell diagnostics contract is consumed by both the integration test and quality golden: the fixture produces exactly 2,000 summary and identifier vectors, 120 section candidates, 80 field-rerank candidates, 160 ADR/search-item shortlist entries, 12,000 relevance sections, and 960 exact-rerank candidates. Relevance source selection remains capped at 24 chunks, and exact section work stays strictly below comparing every selected source chunk with all passages. Elapsed build/query observations are reported for diagnostics only; no wall-clock value is asserted or golden-frozen.

P4-03 connects immutable Git input to the established P3 seam: raw exact-OID observation is parsed and reduced once, strict diagnostics are gated, and the placement-free reduced snapshot becomes the existing `SearchMaterialization`. A resolved decision yields one ADR item; a valid decision multihead yields deterministic `ADR@record` candidates. Graph-invalid and zero-head inputs never reach search persistence. Search tables and all six FTS5 tables are written in the same cold database transaction as semantic and diagnostic rows.

The P3-06 quality golden is normally read-only. `--write-p3-06-goldens` is its only Haskell-owned writer and never runs Python or the 2,000-ADR fixture. P4-03 adds read-only schema/logical/diagnostic goldens with the separate explicit `--write-p4-03-goldens` writer. Persisted revision-cache publication, incremental invalidation, unrelated-ADR reuse accounting, corrupt-cache recovery, worktree relevance policy, CLI/Explorer exposure, E2E, and CI/CD remain deferred.
